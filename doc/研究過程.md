# 研究過程

## LLama 2-7b vs Llama3.1-8b-instruct

| 屬性 | LLaMA-2-7B | LLaMA-3.1-8B | 影響 |
|---|---|---|---|
| num_attention_heads | 32 | 32 | 相同 |
| num_key_value_heads | 32 (MHA) | 8 (GQA) | KV cache 結構完全不同 |
| rope_theta | 10000 | 500000 | RoPE 旋轉頻率不同 |
| rope_scaling | None | llama3 type（factor=8, low_freq=1, high_freq=4, orig_max=8192） | 需要 Llama3 專屬 RoPE |
| max_position_embeddings | 4096 | 131072 | 序列長度上限差 32 倍 |

## 已解決問題（2026-03-18）

### Bug 1：RoPE 類型錯誤（fp16 路徑）— 已修復

**症狀**：fp16 輸出垃圾（avg F1 = 0.063），4-bit 和 fp16 結果一樣爛。

**根本原因**：`configuration_llama.py` 的 `_rope_scaling_validation()` 把新版 HF config 的 `rope_type: llama3` 強制覆蓋成 `type: linear`，導致 `_init_rope()` 選了 `LlamaLinearScalingRotaryEmbedding` 而非正確的 Llama3 RoPE。

Linear scaling 對所有頻率統一除以 8，但 Llama3 RoPE 需要 per-frequency 平滑插值：
- 高頻分量：不縮放
- 低頻分量：除以 factor（8）
- 中間頻率：平滑混合

從 position 16 開始 cos/sin 差距就達 1.18（最大值才 2.0），導致所有 attention 計算全部錯誤。

**修復方式**：
- `configuration_llama.py`：`_rope_scaling_validation()` 改為保留 `llama3` 類型，不再強制轉 linear
- `modeling_llama.py`：新增 `LlamaLlama3ScalingRotaryEmbedding` 類別，`_init_rope()` 加入 `rope_type: llama3` 分支
- `longbench_eval.py`：加入 `sys.path.insert` 確保 custom transformers 優先載入

**修復結果**：
- custom fp16 avg F1：0.0635 → **0.2508**（與 pure HF fp16 完全一致）
- 32 層 hidden states cosine similarity 全部 = 1.000000

## 待解決問題（2026-03-18）

### Bug 2：KVQuant 的 CUDA kernels 不支持 GQA（量化路徑）

**位置**：`modeling_llama.py` line 1408-1409

```python
# Note: custom quantized kernels (eager/flash) don't support GQA yet, but sdpa does
# assert (self.num_key_value_groups == 1)
```

作者自己已經註明了：**量化 CUDA kernels 不支持 GQA**，但把 assert 註解掉了，所以不會報錯。

**問題分析**：

LLaMA-2-7B 用 MHA（Q=32 heads, KV=32 heads），LLaMA-3.1-8B 用 GQA（Q=32 heads, KV=8 heads）。

正常 HF 的做法是用 `repeat_kv()` 把 8 個 KV heads 擴展成 32 個再做 attention，但量化路徑**從未呼叫 `repeat_kv`**（只有 SDPA 路徑在 line 2174-2175 有呼叫）。

具體問題：
1. `forward_fused_sparse()` 收到 Q shape `(32, q_len, head_dim)` 但 QuantK cache 只有 8 heads
2. CUDA kernel 名稱含 `mha_batched`，假設 Q 和 K 的 head 數量相同
3. 維度不匹配導致 **attention 計算完全錯誤**，但不會報錯，只是靜默產生垃圾結果

**同時 prefill 的 parallel path 也有問題**（line 1606）：
```python
attn_weights = torch.matmul(query_states, key_states_rope) / math.sqrt(self.head_dim)
# query_states: (1, 32, q_len, head_dim)
# key_states_rope: (1, 8, head_dim, kv_seq_len)
# matmul 結果: (1, 32, q_len, 8) ← 錯誤！應該是 (1, 32, q_len, kv_seq_len)
```

PyTorch 的 broadcast 機制不會報錯，但結果維度完全不對。

**RoPE 差異**：
- `rope_theta`：10000 vs 500000 — 會傳進 QuantK（line 1457），dynamicrope 路徑有處理
- `rope_scaling`：None vs llama3 type — 已修復（見上方 Bug 1）

**結論**：KVQuant 的量化 CUDA kernels（eager attention path）是為 MHA 設計的，不支援 GQA。在 Bug 1（RoPE）修復後，這是 4-bit 量化路徑效果差的剩餘原因。

### 可行方案

1. **用 LLaMA-2-7B 跑 KVQuant**（原作者的設計目標，確保能 reproduce 論文結果）
2. **修改量化路徑加入 GQA 支持**：在 `forward_fused_sparse` 呼叫前對 Q 做 head 分組，或修改 CUDA kernel 支援 GQA — 工作量大
3. **只用 fp16 SDPA 路徑**跑 LLaMA-3.1（`--bits 16`），但這樣就沒有 KV cache 量化的好處
