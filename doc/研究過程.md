# 研究過程

## LLama 2-7b vs Llama3.1-8b-instruct

| 屬性 | LLaMA-2-7B | LLaMA-3.1-8B | 影響 |
|---|---|---|---|
| num_attention_heads | 32 | 32 | 相同 |
| num_key_value_heads | 32 (MHA) | 8 (GQA) | KV cache 結構完全不同 |
| rope_theta | 10000 | 500000 | RoPE 旋轉頻率不同 |
| rope_scaling | None | llama3 type（factor=8, low_freq=1, high_freq=4, orig_max=8192） | 需要 Llama3 專屬 RoPE |
| max_position_embeddings | 4096 | 131072 | 序列長度上限差 32 倍 |

## 已解決問題（2026-03-18）

### Bug 1：RoPE 類型錯誤（fp16 路徑）— 已修復

**症狀**：fp16 輸出垃圾（avg F1 = 0.063），4-bit 和 fp16 結果一樣爛。

**根本原因**：`configuration_llama.py` 的 `_rope_scaling_validation()` 把新版 HF config 的 `rope_type: llama3` 強制覆蓋成 `type: linear`，導致 `_init_rope()` 選了 `LlamaLinearScalingRotaryEmbedding` 而非正確的 Llama3 RoPE。

Linear scaling 對所有頻率統一除以 8，但 Llama3 RoPE 需要 per-frequency 平滑插值：
- 高頻分量：不縮放
- 低頻分量：除以 factor（8）
- 中間頻率：平滑混合

從 position 16 開始 cos/sin 差距就達 1.18（最大值才 2.0），導致所有 attention 計算全部錯誤。

**修復方式**：
- `configuration_llama.py`：`_rope_scaling_validation()` 改為保留 `llama3` 類型，不再強制轉 linear
- `modeling_llama.py`：新增 `LlamaLlama3ScalingRotaryEmbedding` 類別，`_init_rope()` 加入 `rope_type: llama3` 分支
- `longbench_eval.py`：加入 `sys.path.insert` 確保 custom transformers 優先載入

**修復結果**：
- custom fp16 avg F1：0.0635 → **0.2508**（與 pure HF fp16 完全一致）
- 32 層 hidden states cosine similarity 全部 = 1.000000

### Bug 2 補充：SDPA 路徑完全繞過 kcache/vcache（量化路徑失效）

**發現**：`kvquant_model.py` 的 `get_model()` 寫死 `attn_implementation="sdpa"`，因此所有 bits 設定（包括 `--bits 4`）都走 `LlamaSdpaAttention.forward()`，這個路徑完全不使用 `kcache`/`vcache`，改用 HF 標準 `DynamicCache`。

結果：`load_quantizers()` 把 lookup table 載入 `kcache`/`vcache`，但 SDPA forward 從不呼叫它們——實際上不管設什麼 bits，**推論永遠是 fp16**。

### Fix 3：ROUGE-L 評分對齊 LongBench 官方（2026-03-18）

**症狀**：gov_report fullKV ROUGE-L = 0.218，LiveKVQuantP 同條件跑出 0.343。

**根本原因**：KVQuant 自己實作了 document-level LCS ROUGE-L（整篇文章一起算 LCS），但 LongBench 官方和 LiveKVQuantP 使用 `py-rouge`（sentence-level，逐句計算再平均），後者分數系統性較高。

**修復方式**：`longbench_scoring.py` 的 `rouge_l_score()` 改為用 `rouge` 套件：
```python
from rouge import Rouge as _Rouge
_rouge_scorer = _Rouge()
scores = _rouge_scorer.get_scores(prediction, ground_truth)
return scores[0]["rouge-l"]["f"]
```

**結果**：gov_report fullKV ROUGE-L：0.218 → ~0.36（對齊 reference 0.343）

---

### Fix 4：lcc edit_sim 評分對齊官方（2026-03-18）

**症狀**：lcc fullKV edit_sim = 0.154，LiveKVQuantP 跑出 0.653。

**根本原因**：KVQuant 對整段多行輸出計算 character-level Levenshtein，但正確做法是先從模型輸出取第一個有效的 code line（跳過含 `` ` ``、`#`、`//` 的行），再用 `fuzz.ratio()` 對比。

**修復方式**：`longbench_scoring.py` 的 `edit_sim_score()` 改為：
```python
from fuzzywuzzy import fuzz as _fuzz
def edit_sim_score(prediction, ground_truth):
    all_lines = prediction.lstrip('\n').split('\n')
    prediction = next(
        (l for l in all_lines if '`' not in l and '#' not in l and '//' not in l), ""
    )
    return _fuzz.ratio(prediction, ground_truth) / 100
```

**結果**：lcc fullKV edit_sim：0.154 → 0.650（對齊 reference 0.653）

### Fix 5：gov_report decode 速度優化（2026-03-18）

**症狀**：gov_report fullKV 推論 ~29.7s，LiveKVQuantP 同條件 ~17.4s（1.7×）。

**根本原因**：`kvquant_model.py` 的 `run_inference()` 用 Python 逐 token decode loop（gov_report `output_len=512`，等於 512 次 Python→CUDA round-trip），而 LiveKVQuantP 用 `model.generate()` 在 C++ 層跑 loop。

**修復方式**：保留 prefill 不動，decode 改為在 prefill 結束後直接呼叫 `model.generate(next_token, past_key_values=..., max_new_tokens=output_len-1, ...)`；`stop_on_newline` 行為透過 `StoppingCriteria` 保留。

**預期結果**：decode latency 大幅下降，接近 reference 的 17s 左右。

### Bug 2：KVQuant 的 CUDA kernels 不支持 GQA（量化路徑）— 已修復

**原始問題**：

LLaMA-2-7B 用 MHA（Q=32 heads, KV=32 heads），LLaMA-3.1-8B 用 GQA（Q=32 heads, KV=8 heads）。
原版 KVQuant 的量化 CUDA kernels 假設 Q/K head 數量相同（MHA），不支援 GQA：

1. `forward_fused_sparse()` 收到 Q shape `(32, q_len, head_dim)` 但 QuantK cache 只有 8 heads
2. CUDA kernel 名稱含 `mha_batched`，假設 Q/K head 數相同
3. 維度不匹配導致 attention 計算錯誤（靜默產生垃圾結果）
4. prefill path 的 `torch.matmul(query_states, key_states_rope)` 也因 broadcast 機制產生錯誤維度

**修復方式**：

**（一）CUDA Kernel 層（`quant_cuda_kernel.cu`）：加入 `num_groups` 參數**

4-bit kernels 全面加入 GQA 支持，核心邏輯：
```cuda
int q_headid  = blockIdx.z;              // Q head index (0..num_q_heads-1)
int kv_headid = blockIdx.z / num_groups; // 映射到對應的 KV head
int num_q_heads = numheads * num_groups; // numheads == num_kv_heads
```

涉及的 kernel 函式：
- `VecQuant4MatMulKernelNUQPerChannelTransposedRopeMHABatchedFusedOpt`（K-cache attention + RoPE）
- `VecQuant4MatMulKernelNUQPerChannelTransposedMHABatchedFusedOpt`（V-cache attention）
- `SPMV_ATOMIC_BALANCED`（sparse outlier 廣播到所有 Q heads in group）
- `SPMV_ATOMIC_ROPE_BALANCED`（RoPE + sparse + GQA）

Grid launch 的 z-dimension 改用 `num_q_heads`，每個 Q head 一個 block，kernel 內部透過 `/ num_groups` 映射到正確的 KV head。

> 注意：3-bit 和 2-bit kernels 目前仍 hardcode `num_groups=1`（僅 MHA），4-bit 為完整 GQA 支持。

**（二）Python 層（`modeling_llama.py`）：GQA-aware attention forward**

1. **KV cache 大小**：改用 `num_key_value_heads`（而非 `num_heads`）分配 QuantK/QuantV cache
   ```python
   kv_hidden_size = self.num_key_value_heads * self.head_dim
   self.kcache = QuantK(hidden_size=kv_hidden_size, num_heads=self.num_key_value_heads, ...)
   ```

2. **Prefill path**：在 `matmul` 前對 key_states 做 `repeat_kv()` 擴展
   ```python
   key_states_rope = repeat_kv(key_states_rope, self.num_key_value_groups)
   ```

3. **Decode path**：
   - K-cache decode：CUDA kernel 內部處理 GQA head 映射（`num_groups` 參數）
   - fp16 K-cache：`repeat_interleave(self.num_key_value_groups, dim=1)` 擴展後再 attention
   - V-cache：同上述邏輯

4. **Outlier buffer**：改用 `kv_hidden_size` 計算 outlier 數量，適配 GQA 的較小 KV 維度

**（三）C++ binding 層（`quant_cuda.cpp`）**

新增 `num_groups` 參數傳遞給所有 4-bit kernel wrapper 函式。

**修復結果**：4-bit KVQuant 量化路徑在 LLaMA-3.1-8B（GQA, Q=32, KV=8）上正確運作。

### Bug 6：HF `_attn_implementation` 自動覆蓋為 SDPA — 已修復（2026-03-19）

**症狀**：`run.sh` 跑 4-bit 推論時 CUDA assert `index out of bounds` in `apply_rotary_pos_emb`。

**根本原因**：

即使 `kvquant_model.py` 傳入 `attn_implementation="eager"`，HF `AutoModelForCausalLM.from_pretrained` 仍選擇 `LlamaSdpaAttention`（SDPA），完全繞過 KVQuant 的量化路徑。

具體機制：
1. `AutoConfig.from_pretrained()` 返回的 config 的 `_attn_implementation_internal` 是 `None`
2. `_attn_implementation` getter 在 `internal is None` 時 fallback 返回 `"eager"`
3. `from_pretrained` 裡的覆蓋條件 `config._attn_implementation != kwarg_attn_imp` 比較 `"eager" != "eager"` = False
4. setter 從未被呼叫，`_attn_implementation_internal` 仍為 `None`
5. `_autoset_attn_implementation` 看到 `internal is None`，自動選擇 `"sdpa"`

SDPA 路徑（`LlamaSdpaAttention`）不使用 KVQuant cache，decode 時 `kv_seq_len` 只有 1（而非累積的 cache 長度），導致 cos/sin 長度不足，`position_ids` 越界。

**修復方式**：在 `from_pretrained` 之前直接設定 `config._attn_implementation = attn_impl`，確保 `_attn_implementation_internal` 非 `None`：
```python
config._attn_implementation = attn_impl  # 設定 _attn_implementation_internal
model = AutoModelForCausalLM.from_pretrained(
    model_path, config=config, attn_implementation=attn_impl, ...
)
```

**驗證**：修復後 `model.config._attn_implementation` 為 `"eager"`，attention class 為 `LlamaAttention`（KVQuant 版）。

## 2026-03-19-130000 - Bug 7：CUDA kernel K-cache RoPE 未實作 Llama3 Scaling

**症狀**：narrativeqa（bits=4）avg F1 = 0.031，遠低於 fp16 baseline 0.284。輸出語無倫次（重複 token），decode latency 異常慢（fp16: 1088ms vs 4bit: 11399ms，慢 10×）。multifieldqa_en（output_len=64，短序列）F1=0.287 看起來還算正常。

**根本原因**：

Llama-3.1-8B 使用 `llama3` 型 RoPE scaling（low_freq=1, high_freq=4, factor=8）：
- 高頻分量：不縮放
- 低頻分量：除以 factor=8
- 中間頻率：smooth_factor 平滑插值

**Python 層**（`apply_rotary_pos_emb_query`）：使用正確的 Llama3 RoPE，有 per-frequency scaling。

**CUDA kernel**（`VecQuant4MatMulKernelNUQPerChannelTransposedRopeMHABatchedFusedOpt`）：只用標準公式 `theta = powf(rope_theta, -2i/d)`，沒有 Llama3 per-frequency 平滑插值。

結果：Q·K^T 時 Query 用 Llama3 scaling 的 cos/sin，K cache 用標準 cos/sin，兩者不一致 → attention weights 錯誤 → decode 崩潰。短序列低位置差異不顯著，長序列高位置差異巨大（低頻分量差 8×）。

**修復方式**：在 CUDA kernel 加入 Llama3 per-frequency scaling，詳見 Bug 7 修復記錄。

**修復結果**：narrativeqa avg F1：0.031 → **0.4447**（fp16 baseline: 0.456，差距僅 2.4%）。

## 2026-03-19-132000 - Bug 7 修復：CUDA kernel 加入 Llama3 RoPE Scaling

**任務**：修復 CUDA kernel K-cache 的 RoPE 計算，使其符合 Llama3 per-frequency scaling。

**修改的檔案**：
1. `deployment/kvquant/quant_cuda_kernel.cu`：
   - `VecQuant4MatMulKernelNUQPerChannelTransposedRopeMHABatchedFusedOpt`（forward decl + 實作）：加入 4 個參數 `llama3_orig_max_pos, llama3_low_freq_factor, llama3_high_freq_factor, llama3_scaling_factor`；theta 計算後加入 Llama3 per-frequency scaling（`llama3_orig_max_pos > 0` 才啟用）
   - `SPMV_ATOMIC_ROPE_BALANCED`（forward decl + 實作）：同樣加入 4 個參數；sparse outlier RoPE 也同步修正
   - 3-bit、2-bit kernel 及 orig_sparse 路徑的 SPMV_ATOMIC_ROPE_BALANCED 呼叫：傳入 `llama3_orig_max_pos=0.0f`（停用）
2. `deployment/kvquant/quant_cuda.cpp`：更新 4-bit rope 函數的宣告與呼叫，加入 4 個新參數
3. `deployment/transformers/src/transformers/models/llama/modeling_llama.py`：
   - `QuantK.__init__` 加入 `rope_scaling=None` 參數，解析 Llama3 scaling 參數並儲存
   - `forward_fused_sparse` 中 4-bit kernel 呼叫加入 llama3 scaling 參數
   - `LlamaAttention.__init__` 初始化 QuantK 時傳入 `rope_scaling=self.config.rope_scaling`

**Llama3 scaling 公式**：
```
theta = base^(-2i/d)
wavelen = 2π / theta
if wavelen > orig_max / low_freq_factor:  theta /= scaling_factor  (低頻)
elif wavelen >= orig_max / high_freq_factor:  smooth blend  (中間)
else:  unchanged  (高頻)
```

**驗證結果**：
- narrativeqa 10 samples：F1 **0.031 → 0.4447**（fp16 baseline 0.456，差距僅 2.4%）
- avg decode: 1018ms（修復前 11399ms，慢 10x；現在正常）

**下一步**：
- 跑完整 benchmark（narrativeqa、multifieldqa_en、hotpotqa、gov_report 等）取得完整數字
- 與 fp16 baseline 對比量化損失

## 2026-03-19-140000 - Latency 分析：4-bit vs fp16

**觀察**：narrativeqa 15 samples 端到端比較：

| 指標 | fp16 | 4-bit | 說明 |
|------|------|-------|------|
| avg F1 | 0.4513 | 0.4437 | 量化損失僅 ~1.7%，合理 |
| avg prefill | 4548ms | 10496ms | 4-bit **慢 2.3×** |
| avg decode | 1048ms | 1023ms | 幾乎持平（論文宣稱 1.2-1.6× 加速） |
| max memory | 33940MB | 28205MB | 節省 ~5.7GB |

**Prefill 慢 2.3× 的原因**：
- Prefill 階段需對每個 token 做量化壓縮（outlier 偵測、topk、lookup table 索引），這個壓縮有顯著 overhead
- narrativeqa prompt 很長（7K-18K tokens），overhead 放大
- 論文提到 prefill 用 fp16 計算再壓縮，壓縮本身是額外成本

**Decode 沒有加速的原因**：
- 論文 Table 6 benchmark 條件：LLaMA-2-7B-32K on A6000 GPU（隔離 kernel 測試）
- 我們使用 LLaMA-3.1-8B + 不同 GPU，且端到端有 Python overhead、GQA head 額外計算等
- 論文加速效果在長序列更明顯（l=16K 時 1.7×），短序列有限
- decode kernel 本身（~1023ms）已接近正確，主要是端到端環境差異

**結論**：4-bit KVQuant 的主要價值是 **memory 節省**（使 long context 可行），latency speedup 是硬體相關的次要效果，在論文的 isolated benchmark 條件下才最明顯。
