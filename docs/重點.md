# 重點

## 寫論文必看
論文中提到 prefill 使用 fp16 計算後再壓縮到低精度儲存，壓縮本身有成本。narrativeqa 的 prompt 很長（~7K-18K tokens），所以 prefill overhead 很明顯。論文的 benchmark（Table 6）是測 decode 的 kernel latency，不包含 prefill 的壓縮時間。

## 改動
✅ 必要的改動（支援 LLaMA-3.1-8B）
1. GQA 支援（num_groups 參數）

CUDA kernel 加入 int q_headid / num_groups 映射到 KV head
Python 層改用 num_key_value_heads=8 分配 QuantK/QuantV
這只是讓原有的 Pre-RoPE Key Quantization 正確執行，沒有改變方法本身
2. Llama3 RoPE Scaling 加入 CUDA kernel

論文 Section 3.2 明確要求：CUDA kernel 內 on-the-fly 套用 RoPE
LLaMA-3.1 的 RoPE 本來就與 LLaMA-2 不同，kernel 內要套用正確的 RoPE 才符合論文精神
這是讓「Pre-RoPE Key Quantization」方法在新模型上正確運作，不是改變方法
3. configuration_llama.py 保留 rope_type: llama3

原版 bug：強制把 llama3 轉成 linear，導致 RoPE 算錯
支援新模型的必要修正
⚠️ 需要確認的改動
fp16 路徑修正（modeling_llama.py）

改為：abits < 16 才分配 QuantK/QuantV，fp16 用標準 HF cache
這不是為了 LLaMA-3.1，而是修正了原版的 bug
但這不影響 KVQuant 方法本身（方法是 sub-16bit 量化）
LlamaLlama3ScalingRotaryEmbedding 新類別

這是 Query 端的 RoPE（fp16 prefill path）
只是讓模型能正確計算 Llama3 的 cos/sin，不影響 KVQuant 量化邏輯
❌ 真正可能有問題的地方
目前看起來改動都在「讓 KVQuant 方法在 LLaMA-3.1 上能正確運作」的範圍內，沒有動到：

NUQ（非均勻量化）的 lookup table 機制
Per-Channel Key Quantization 的 scaling factor 計算
Dense-and-Sparse（outlier 偵測）的邏輯
Attention Sink-Aware（first_few_fp16）的邏輯
Offline calibration 的流程
唯一需要注意的：原版 3-bit / 2-bit kernels 的 num_groups hardcode 為 1（MHA only），目前沒有修改。如果未來要測 3-bit / 2-bit，GQA 支援不完整，結果會是錯的。
